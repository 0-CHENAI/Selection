# marker-v1 正文分界验收（2026-09-17）

> 2026-09-24 更新：模型在真实回答中输出过错误的起始标记和多余的结束标记。普通会话即使仍配置 `streaming + marker-v1`，现在也改用 `submit_answer` 结构化交付；已有记录仍按原协议读取。下文为 2026-09-17 的历史验收结果。

## 实现与启用

普通会话可在 LLM connection 上设置 `answerDelivery: "streaming"`、`presentationProtocol: "marker-v1"`。未设置协议的连接维持 `legacy`；`native` 供已确认能提前提供 phase 的接口使用。不改变结构化任务、子会话和 explicit-v1 工具交付协议。

模型在独立行输出 `<<<FINAL_ANSWER>>>`。Pi 适配器在进入 SessionManager 前拆分过程和正文，使用不同 turnId；过程完成事件先于正文增量，避免主进程缓存串段。presentationProtocol 和 phase 经批处理、事件处理和持久化保留。正文开始并不代表已完成，也不改变工具权限。

漏标记时仅在正常完成后展示末条回答，记录 missing_boundary，不自动重试。重复/空标记及正文后工具调用记录独立异常。原始 SDK 历史保留；UI 不显示合法协议标记。代码围栏与引用示例不触发分界。取消/错误保留已收到内容，不能升级为成功回答。

前端只对 final 片段使用正文卡片，已完整接收的 Markdown 块才参与布局；末尾列表、引用等待顶层块分界，代码块内部空行不触发显示。首段开始即有白框，完成只增加操作栏。计数按最新约定统计工作记录总数（含过程说明，排除空白临时占位，工具事件按调用ID去重），自动滚动保留用户上滚取消跟随。

当前仅本机 pi-api-key-2 启用了 marker-v1；其他连接没有自动迁移。回滚该连接的 presentationProtocol 为 legacy 即停止注入标记提示，新记录仍保留分类。

## 实际接口证据

使用当前 Laufry 的真实 Chat Completions SSE，经实际 PiEventAdapter、前端 text handlers、groupMessagesByTurn 和段落选择器回放。单位毫秒，从请求开始计时；这里的“首段”是前端状态中可渲染的首段，不是浏览器 DOM 时间。

| 场景 | 首个 final 增量 | 首段可渲染 | 请求完成 | 内容增长次数 |
| --- | ---: | ---: | ---: | ---: |
| 无工具六段回答 | 2199 | 2200 | 4487 | 7 |
| 两次官方文档查询，注入一次读取失败后重试 | 13094 | 13094 | 15427 | 7 |
| 列表、表格、代码、Mermaid（重跑） | 4136 | 4137 | 6656 | 13 |
| 首段后中止 | 3606 | 3806 | 3807 | 1 |

文档查询测试由脚本执行真实官方页面读取，失败为显式故障注入，不是上游自然故障。富文本首次 max_tokens=2400 时耗尽预算，未产生可见正文；提高测试预算到8192后通过。该失败保留，不能算作流式成功。

进一步使用真实 PiAgent + pi-agent-server 子进程 + 完整应用系统提示验证：

- 首次无工具测试出现标记前先写完整草稿、标记后重写的问题。协议补充“无需工具直接以标记开头、之前不得写答案草稿”，并放到稳定系统提示末尾。
- 加强约定后的无工具测试：229 个文本增量；首个 final 在13017ms，结束15969ms；只有一个最终片段（640字符），未泄漏标记。
- 加强约定后的两次官方文档 WebFetch 流程：338 个文本增量；3个过程片段（27、56、46字符），1个最终片段（1602字符）；首个 final 在34539ms，结束37951ms；未泄漏标记。

最终提示的两个完整 PiAgent 样本中，漏标记0/2、正文后工具调用0/2；初版提示仍有一次标记前重复草稿的失败。两个样本不足以估计生产可靠性。没有自动增加修复请求。

## Token 成本

同一个实际接口、相同用户消息与 max_tokens=1：基线 prompt_tokens=19，加入最终版提示后124，增量105。仅加入标记的 prompt_tokens=25，输入编码增量6。接口没有按输出片段提供 usage，因此6不应被声称为已测量的标记输出计费 token 数。
