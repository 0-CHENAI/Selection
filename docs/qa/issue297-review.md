# #297 超时诊断与失败恢复验收

## 客户端实现

- 网络请求发出后发生错误时，拦截器直接传播错误，不再走请求修改失败的 fallback 重发原请求。HTTP/SDK 和节点重试仍由各自显式策略控制。
- 每次 SDK stream invocation 使用独立 AsyncLocalStorage 上下文。每次 HTTP 请求有独立 ID、attempt 和阶段；后发请求清除旧请求元数据，旧请求的迟到回调不能覆盖新请求。
- 诊断附着于对应的 SDK 错误消息跨进程传递，不再通过会话级“最后一次错误”推断归属。未知错误也使用 typed_error 保留详情。
- 覆盖请求前失败、HTTP 非成功响应、SSE 上游错误、无效事件、断流与取消。记录受限的服务端 request ID、HTTP 状态、阶段、耗时和请求尝试次数及首字节/首次输出时点；不记录正文、URL、工具参数或错误原文。
- SSE 观察保持字节与取消语义；按 CR/LF/CRLF 解析，64 KiB 上限，每种诊断每请求最多一次。心跳、事件与模型输出分开记录。

## 恢复合同

- 失败节点及受影响下游重新执行；无关成功节点及失败 map/replicas 的成功兄弟保留。
- 已完成的 all_done / finally 等下游可能依赖失败状态，必须失效重新执行；界面明确提示工具操作可能重复。
- 循环从失败迭代继续并保留成功前缀；耗尽的循环显式重试时重新开始，但历史 attempt 与预算不清零。
- 审批重新进入等待状态，不能因重试自动同意；verify/judge 的旧 verdict 失效，必须重新提交。
- V3 恢复仍经过 coordinator gate；最终验收失败可重新进入验收流程，不绕过预算或质量门。
- 一条 run-resumed 事务记录重置节点及失效实例。内存恢复和日志重放使用同一重置逻辑；实例历史尝试编号保留，旧日志缺失实例终态的情况可恢复。

## 验证

- 真实拦截器 preload + Pi SDK 子进程：无心跳和有心跳的 10.1 秒首 token 均成功；精确英文超时、未知 SSE 错误、无效 JSON 事件和 HTTP 拒绝均保留对应请求诊断。
- 打包后的 Pi 服务配合独立 preload：实际 message_end 保留对应 HTTP 200 SSE 错误的 request ID 和阶段。
- 模拟 originalFetch 抛错：只发送一次请求，拦截器不隐式重发。
- 并发调用及同调用多次请求：诊断互不串用，旧回调不能覆盖当前失败。
- Conductor / V3 定向回归覆盖简单 DAG、map、replicas、审批、循环、reviewer、coordinator gate、下游失效和重启恢复。

- 最终代码执行 `bun run validate:ci` 通过：全项目类型检查、测试、lint（0 errors）、国际化一致性/排序/覆盖率均通过；Conductor 与 V3 定向回归 118 项通过。
