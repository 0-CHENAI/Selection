# 产品需求文档

用户要 PRD、产品需求说明或功能说明时用本技能。成品是 Word。文档说明要做什么、为谁做、怎样算做完。不代替技术方案，不写无依据的排期承诺，不把样例小程序的功能抄进用户的产品。

## 章节

1. 背景：现在的问题，只写用户提供的事实。
2. 目标：可检查的结果。非目标单独一节，写明这次不做什么，避免范围被后文悄悄扩大。
3. 用户与场景：谁在什么情况下使用。没有研究数据就不写「用户普遍认为」。
4. 用户故事：作为谁，我要做什么，以便哪一个目标。每条故事下写验收标准。
5. 验收标准：用「给定、当、则」或编号条目，每条都能被勾成通过或失败。避免「体验良好」「尽量快」。速度、数量若没有用户给的数，标待补充。
6. 范围外与待定问题。待定用「待补充」，并写谁来定，如果用户没说谁，就写「待补充：决策人」。
7. 里程碑：名称、目标日期、进入标准。日期用户没给就标待补充，不按「两周一期」自行铺开。里程碑不是甘特图；用户要工期和依赖时改用项目计划技能，本文只留名称和日期。

## 写法

- 一条需求一个编号，后文引用编号，不重复改写成另一句话。
- 界面只描述用户确认过的元素。没给稿时写行为，不画一套虚构按钮还当成已经定稿。
- 指标来自用户。没有基线就不写「提升 20%」。
- 术语第一次出现时用用户的叫法，不另起一套产品黑话。

## 版式

- A4，标题用标题样式，正文宋体或等线、小四，1.5 倍行距。
- 用户故事和验收标准用编号，不用大段没有标题的文字。
- 表格只用于「故事 / 验收 / 待定」对照。表头重复。
- 页眉写产品名和「需求说明」，页码在页脚。产品名未知就标待补充。
- 不放无来源的竞品截图。

## 自检

- 每个目标至少有一条故事或明确写「待补充：对应故事」。
- 每条故事至少有一条可失败的验收标准。
- 非目标里排除的内容，没有在后文又被写成要做。
- 样例小程序的页面、指标、日期没有残留。
- 里程碑日期要么来自用户，要么是待补充。
- `validate` 已通过。`office_render` 抽查首页和故事表，标题层级清楚，表格不溢出。

## 常见错误

- 把技术方案的表结构写成需求本身。用户没要设计时，数据只写到「需要记住什么」。
- 验收标准复述故事，没有判断条件。
- 用「等」「相关功能」扩大范围。
- 把季度 OKR 的分数表贴进 PRD 当目标。可以引用目标原文，不引入权重公式。

## 文件交付

先 `officecli load_skill word`。不要用 Python 或 LibreOffice。样例只读，只学章节顺序。交付前走版式守卫。
