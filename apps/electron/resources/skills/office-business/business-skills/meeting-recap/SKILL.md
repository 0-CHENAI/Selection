# 会议纪要

根据当前用户材料整理一份供参会人确认、项目组执行的纪要。重点是决定了什么、仍需确认什么、谁负责推进以及何时交付。所选 DOCX 案例提供版式，当前用户材料提供事实。

## 1. 读取材料并建立事实依据

完整读取文字稿、会议笔记和附件，记录文件名与段落、时间戳或发言位置。长材料先按议题分段，再合并同一议题的重复讨论。保留涉及范围、数值、条件、责任和时间的原文依据。

会议信息取自材料：名称、日期、时间、方式、参会人、主持人。已有信息直接填写，缺失字段统一写“待确认”。记录人填写用户指定的人；材料中出现的发言人和正式参会名单分别识别。

文件元数据与口述会议时间分别记录其来源。基准日期确认后再换算相对期限；元数据的正确性根据证据判断，已有日期只按材料明确的含义使用。

多人名、缩写或 ASR 误识别先用上下文和附件核对；仍有歧义时保留原称呼，并集中列出待确认点。根据已有素材先完成初稿，关键矛盾放在交付时提醒用户。

## 2. 按原文确定事项状态

每个事项先归入以下状态，再写入纪要：

| 状态 | 依据 | 写法 |
| --- | --- | --- |
| 已定 | 明确确认、共同接受或有决策权限的人员作出决定 | 写清决定内容、适用范围、生效条件 |
| 建议 / 讨论 | 提议、个人观点、备选方案 | 保留提出者、理由及讨论结果 |
| 待决 | 明确留待评估、审批或补充材料 | 写清待决问题、决策条件和下一步 |
| 已调整 | 后续明确修改或撤回前一安排 | 采用最后明确安排，并保留调整原因 |

“暂定”“建议”“可能”“客户确认后”“评估通过后”等条件随结论保留。“同意评估方案”对应评估任务；正式采用方案的状态由明确的采纳决定确定。

数值保留原单位、统计范围和时间口径。发生冲突时，列出冲突的两处依据及需要确认的字段。跨多场会议整理时，按会议日期与事项版本追踪最终决定。

## 3. 提取行动项

原文出现明确工作或承诺时，提取任务、负责人、期限和交付标准。每项任务使用“动词 + 对象 + 完成条件”描述。相同任务合并为一项，关联对应议题。

- 负责人来自明确指派或认领；材料只写“产品侧”时保留“产品侧”，缺失时写“待确认”。
- 期限按原文记录。明确日期统一为 YYYY-MM-DD；“下周”“月底”等表述保留原话，必要时附材料已提供的基准日期和待确认的具体时间。
- 优先级在原文明示时填写；交付标准来自会议要求，缺失时写“待确认”。
- 行动项集中展示在一张表里。议题正文说明决定、背景和关键分歧。
- 本次明确没有新增任务时，写明这一结果，并省略空表。

工作组职责、愿景或一般原则放在议题记录中；已经完成的工作作为进展或决策依据展示。

## 4. 组织可读的纪要

默认采用以下结构，按实际内容长短调整页数：

1. **会议名称与会议信息**：紧凑展示时间、方式、参会人和会议目标。
2. **结论与待决事项**：先给出关键决定及生效条件，读者可以快速掌握结果。
3. **议题记录**：按主题组织背景、关键讨论、决定或待决状态。详细程度随用户要求和材料复杂度调整，保留影响判断的理由与分歧。
4. **行动项**：任务、负责人、期限、交付标准；需要追溯时增加“来源”列。
5. **待确认事项**：集中列出缺失信息、矛盾和依赖；内容齐备时省略。

同一事实在结论、议题和行动项之间保持一致。正文使用自然、明确的业务语言；标题、编号和表格承担信息层级。建议、风险推测和后续写作建议若有价值，单独标为“整理建议”，与会议决定分别呈现。

## 5. 制作 Word

用户选择会议纪要案例时，只读 `cases/meeting-minutes/example.docx`。把原件复制到会话工作区后再改，禁止覆盖案例目录里的文件。

先调用 `office_template(template_id="meeting-minutes")`，按返回的段落 / run ID 用 `office_template_write` 写出新的 DOCX：replacements 替换示例事实，additions 用 `style_from` 继承原段落样式，行动项超出示例行数时用 row_additions 克隆表格行。宿主在写出和交付前自动跑版式守卫，未通过时按诊断修正后重写。需要 OfficeCLI 时先读 [OfficeCLI 路由](../../officecli/SKILL.md)，执行 `officecli load_skill word`。

沿用所选原件的 A4 纵向、约 2cm 页边距及原生标题样式。Title 约 23pt、Heading 1 约 14pt、Heading 2 约 12pt，黑色；正文 11pt、精确 16pt 行距。标题设 keep_with_next，与后文保持相邻。Title 样式与标题段落不带边框；段落 snapToGrid 为 false，保持实际行距。原件字体随副本保留；换字体时先看返回的 `font_warnings`。

会议案例的行动表为“任务与交付要求 / 责任分工 / 期限”三列，宽度 10.2 / 3.1 / 3.7cm。任务单元格按任务、交付标准与来源分层呈现，责任和期限居中。改列宽时同时改 tblGrid 的 gridCol 与每个单元格的 tcW，两者保持一致。表格段落用精确 14pt 行距，行高自动，保留单元格内边距、完整表格行与重复表头；页脚沿用 PAGE / NUMPAGES 字段。行动项数量与页数由当前材料自然形成。

用当前用户材料替换案例中的示例事实，保留标题样式、可编辑段落及表格。不使用 python-docx，不调用安装级 Python，不调用 LibreOffice Kit。有 `office_render` 时导出 PDF 逐页复核：标题与后文是否同页、三列宽度、尾页密度、字体诊断；没有页图时写「视觉检查未做」，不以缺页图冒充通过，不用 OCR。

结构检查调用会话工具 `office_business`，command 为 `validate-minutes`，传入纪要 Markdown 或工作区内的路径。退出码 0 表示章节、表格字段、日期和重复任务通过。该检查不证明事实与原文一致。安装包不带 Python；计算在应用进程内完成。仓库里的下面这条命令只用于开发对拍：

```bash
bun packages/office-business-runtime/src/cli/validate-minutes.ts 会议纪要.md
```

交付物是工作区中的 DOCX，由 Selection 的文件卡片呈现。

## 6. 质量复核

交付前逐项核对：

- 每条决定有原文依据，状态与生效条件一致。
- 发言、建议、已定和待决事项准确区分，后续调整已更新。
- 人名、范围、数字、单位和日期均与当前材料对应。
- 行动项覆盖原文明确工作，负责人和期限保留材料口径，缺失字段标为待确认。
- 每项任务只在行动项表中登记一次，议题和汇总之间的信息一致。
- 当前 DOCX 的示例内容已由本次会议事实完整替换，案例原件的 sha256 未变。
- `office_business` 的 validate-minutes 已通过。
- 版式守卫已通过；逐页页图检查已做，或明确记为未做。

可选运行上面的校验命令。脚本验证结构；事实准确性由原文逐项核对。
