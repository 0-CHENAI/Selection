# 简历与求职信

用户要简历、履历或求职信时用本技能。成品是 Word，简历在前、求职信另起一页。不编造公司、职位、学历、证书和业绩数字。用户没写的经历标「待补充」，不从样例或岗位说明里借一段填上。

## 先分清两份文件

- 简历列事实：谁、在哪、做了什么、结果是什么。
- 求职信解释为什么是这个人和这个岗位。它不是把简历再叙述一遍。
- 用户只给了简历、没要信，就不要另写一封。用户只给了 JD、没给经历，先问经历，不要用 JD 的职责写成「本人负责」。

## 动笔前要有的材料

1. 姓名，以及用户愿意公开的电话、邮箱、城市。身份证号、银行卡、家庭住址、照片，用户没明确要求就不写。
2. 目标岗位和岗位说明。没有岗位说明时，简历按用户现有经历整理，不猜测关键词。
3. 每段经历的机构、起止时间、角色。时间对不上就标待补充，不要写成「至今」来掩盖空档，除非用户就是这么说的。
4. 能写进结果的数字：用户给了才写。没有数字就写做了什么动作，不写「提升了 30%」。
5. 学历、证书、语言。证书名称以用户原文为准。

## 简历结构

中文简历默认一页。经历很多、用户明确要两页时才到第二页。英文简历同样控制篇幅，条目用过去时，省略「I」。

1. 抬头：姓名、目标岗位、电话、邮箱、城市。
2. 一段三行以内的摘要，只概括材料里已经出现的方向，不写「充满激情」。
3. 工作或项目经历，近的在前。每条用 STAR：情境一句话、任务一句话、动作、结果。结果必须能在用户材料里找到。
4. 教育。
5. 技能与证书。技能词从用户材料和岗位说明的交集里选，不把岗位说明整段抄成技能清单。

版式：页边距不窄于 1.6 厘米。姓名用黑体、大于正文；正文宋体或等线、小四或五号。一段经历内的要点用项目符号，不用表格套整页。颜色只用一种深色，不放进度条和自评星级。

## 求职信结构

另起一页，不超过一页。

1. 日期、称呼。不知道招聘负责人就写「招聘负责人」，不编姓名。
2. 第一段：申请什么岗位、从哪里得知。
3. 第二段：用一两件用户已经写过的事说明匹配，不新增经历。
4. 第三段：希望的下一步，例如面试。不写薪资，除非用户要求并给出了数字。
5. 结尾敬语和署名。

英文信的称呼、日期格式和结尾见英文商务信函技能的信头规则；内容仍然只来自这份简历材料。求职信不要改走那份技能的合作邀约结构。

## 自检

- 每一句经历都能指回用户材料。样例里的公司、产品、数字没有残留。
- 简历没有身份证号和详细住址。
- 中文简历在一页内，除非用户要求两页。求职信单独成页。
- 岗位关键词出现在真实做过的条目里，而不是堆在一个与经历无关的词云里。
- 时间顺序没有重叠到用户没解释过的程度。重叠时标待补充，不自行删掉一段。
- `validate` 已通过。看页面用 `office_render`，不用 OCR。检查有没有字被挤出页边、要点是否只剩半行。

## 常见错误

- 把岗位说明里的职责写成候选人的成绩。
- 为了凑一页，把样例的项目经历留在稿里。
- 求职信重复简历的全部要点，没有说明为何申请这个岗位。
- 英文简历保留中文的「负责」「参与」直译成长句。改成动词开头，但不增加事实。
- 照片、婚育、政治面貌，用户没要求就不要主动加。

## 文件交付

用 OfficeCLI 写 DOCX，先 `officecli load_skill word`。不要用 Python 或 LibreOffice。样例只提供一页简历加一页求职信的版式。姓名、公司、岗位和结果全部替换。交付前走版式守卫。用户没要 PDF 时不导出。
